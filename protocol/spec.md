# 传书 ChuanShu 传输协议 v1

机器可读契约在同目录 `protocol.json`（端口、分块大小、错误码、端点清单）。本文件解释
**为什么这么定**以及两端必须一致实现的语义。PC 端（`app/net/`）与手机端（`shared/protocol/`）
都以此为唯一真相源；改协议必须先改这两份文件，再动代码。

## 0. 角色：对等，不固定谁收谁发

每个运行中的实例同时是 server 和 client：监听一个端口、广播自己的存在、既能发也能收。
文件互传意味着手机和 PC 都要能发起，所以协议里没有"主控端"概念。

代价写在 §6「保活」——手机端当接收方时必须保持可连状态，这是各平台限制最集中的地方。

## 1. 身份

| 字段 | 生成 | 存放 |
|---|---|---|
| `peer_id` | 首次运行随机 16 字节 hex | 本机身份目录里自己的文件，文件名不属协议 |
| `keypair` | Ed25519，首次运行时生成 | 同上，私钥文件权限按平台收紧 |
| `fingerprint` | 身份密钥 SPKI 的 SHA-256 hex | 派生值，不落盘 |
| 服务叶 | RSA-2048，自签 X.509（CN=peer_id，20 年），首次运行时签发 | 同目录里自己的两个文件（PC 叫 `tls-leaf.pem` / `tls-leaf-key.pem`），文件名不属协议 |
| `served` | 服务叶证书 SPKI 的 SHA-256 hex | 派生值，不落盘 |
| `name` | 用户可改的设备名 | 用户目录 `settings.json` |

`keypair` 那一行不写证书形状，因为三端各存各的：PC 把自己的 Ed25519 包成一张自签 X.509（CN=`peer_id`），
装载时从那一张的 CN 读回 `peer_id`；安卓与鸿蒙只存私钥种子和那份 SPKI，纸面上没有那张证书。线上同样没有——
§3 的 pair 请求带的是 32 字节裸公钥，收方自己拼出 SPKI 再取摘要，算出来的与发方从自己材料里取的是同一个数
（#106 逐字节核过）。协议钉的是**摘要**，不是证书，所以没有任何一端去读那张证书的新旧；这一行留下来的只有
一句各端都照做的形状：`peer_id` 是 16 字节随机 hex，鸿蒙装载时还会量它是不是 32 个 hex 字符。

一台设备有**两个摘要**，各管各的：`fingerprint` 说"这是哪台机器"——配对签名用它、信任库以它为键、
配对回复和 hello 的 `fingerprint` 字段是它；`served` 说"这个套接字递出的是哪张证书"——二维码的 `f=`、
广播里的 `fp` 前缀、TLS 钉子和 hello 的 `served` 字段都是它。之所以不是一把钥匙：没有任何平台能把自己
的 Ed25519 密钥当 TLS 叶签出去——鸿蒙的平台 TLS 签不出 Ed25519（#47），Android 的 Conscrypt 在
signature_algorithms 里根本不广告 ed25519、且 android.jar 34 的 `SSLParameters` 没有 setter 能加上，
同一个端口握手只会回 `SSLV3_ALERT_HANDSHAKE_FAILURE`（#106）。所以三端一致：身份密钥只签名，服务叶只
服务。

`peer_id` 会随重装变化，**信任锚是 fingerprint，不是 peer_id**。同一 fingerprint 换了
peer_id 视为同一台设备。

换过服务叶的设备（例如本改动之前的 PC），对端已经钉死的那张叶不再匹配，**已有配对需要重新配一次**；
这不是协议破绽，钉子本来就是钉证书的。

## 2. 发现

三条路径，实现时按顺序尝试，任一可用即可配对：

1. **mDNS**：注册 `_chuanshu._tcp.local.`，TXT 带 `ver`、`name`、`fp`（服务叶摘要的前 16 位）、`ts`。
   iOS 必须在 Info.plist 的 `NSBonjourServices` 里声明 `_chuanshu._tcp`。
2. **UDP 广播 43721**：每 3s 发一次 `{peer_id, port, v, name, fp, ts}`，监听常驻。多播在部分
   环境（iOS 新版本、鸿蒙卓易通兼容层）会被拦，所以它是补充而非依赖。
3. **扫码/手输 IP**：二维码里带齐 §3 的全部字段，不依赖任何发现协议。发现失败时 UI 必须
   直接给出这条出口，不能只写日志。

前两条广播只带 **服务叶摘要的前缀**，不带完整摘要：广播本身不构成信任，前缀只用来排除
"地址撞错机器"。完整摘要由 `GET /v1/hello` 的 `served` 字段给出，收到候选后必须先核对
前缀再进入 §3 配对。之所以是 `served` 而不是 `fingerprint`：核对发生在套接字上，读回来的是对方
实际递出的那张证书的摘要，而按 §1 那可能不是身份密钥（老构建只有 `fingerprint` 一个字段，那时两者
是同一个数，取不到 `served` 就退回它）。"完整指纹 + 同屏 6 位码"两个条件同时成立才算配对成功——单靠
广播谁都能发一份，这一点不能骗自己。

## 3. 配对（TOFU + 带外确认）

接收方显示二维码：

```
chuanshu://p?h=<host>&p=<port>&v=<protocol_version>&f=<fingerprint_hex>&c=<6位配对码>&k=<连接密码>
```

`c` 是一把**固定配对码**：设备首次启动时生成，写进身份目录，之后不再自动过期，二维码因此可以打印、
可以反复扫；只有用户点「更换配对码和密码」时才换新生成的一组，旧的当场作废。`k` 是同一份材料里的
8 位连接密码（字母表去掉易混的 I/O/0/1），扫码方与手输方拿到的是同一个承诺。`h` 会随本机所在网络变化，
所以端口/地址变了画面要重画，与码是否固定无关。

旧版本（只认 `pair_code_ttl_s` 的构建）可以继续按 120s 轮换自己的码：两端各自决定自己显示什么，
`c` 的校验只看"对方屏幕此刻显示的那串"，不校验它存在多久。

`f` 是完整的 64 位十六进制 SPKI 指纹，不是界面上展示的前缀；它说的是**这台设备 TLS 服务实际递出来的那张
叶证书**的摘要。两端读取配对信息时都拒绝缺 `h`/`f`、`f` 不是 64 位十六进制（复制被截断）、`v` 不是本机
支持的版本、`p` 不是数字；`h`+`f`+`v` 是必需的，`p` 缺失时用默认端口，未知键忽略。这张叶现在每一端都不是
身份密钥：鸿蒙的平台 TLS 签不出 Ed25519（#47），Android 的 Conscrypt 不广告 ed25519、`SSLParameters` 也
加不上（#106 实测），PC 因此同样挂一张 RSA-2048 叶——身份密钥只负责签名。所以 `f` 与界面显示的
「身份指纹」是两个数，配对信息里放的是前者，配对报文里两个都点名（见下面 `tls_fingerprint`）。只有还在
用身份密钥签自己证书的老构建，`f` 才同时就是身份指纹。

发送方对 `https://h:p` 发起 `POST /v1/pair`，TLS 校验只认 `f`（自建 CA 不存在）：

```json
{"peer_id": "...", "name": "...", "nonce": "...", "public_key": "<base64 raw ed25519>",
 "signature": "<base64>", "code": "417392", "secret": "K7QMXZ2P", "tls_fingerprint": "...",
 "protocol_version": 1}
```

`public_key` 是发送方的**身份密钥**，`signature` 签的是竖线拼起来的断言本身：

* 省略 `tls_fingerprint`（叶就是这把身份密钥自己签的，只有还在这么发的老构建）：`pair|<peer_id>|<nonce>`；
* 带上 `tls_fingerprint`（本机服务的叶是另一把钥匙，现在的 PC、Android、鸿蒙都走这一条）：
  `pair|<peer_id>|<nonce>|<tls_fingerprint>`，值就是本机那张叶的完整指纹。

接收方按**这一格有没有值**决定验哪一条——键不在、值是 null、值是空串，这三种在这条线上都算"没带"（PC
读的是 `str(body.get("tls_fingerprint") or "")`，共用内核读的是 `body.getString('tls_fingerprint', '')`），
所以已经发出去的构建不会因为多了一个字段而验不过，新构建也不会拿三条去签。这个键解决的是"一台设备两个指纹"：对方凭签名把它的身份指纹记成信任，本机凭 `f` 把它的
叶记成 TLS 钉子，两个数字指的是同一台机器；没有这句话，同一台挂独立叶的设备会被算成两台，"一次只连一台"
会自己把自己锁住。有了这句话，接收方可以按身份指纹认出设备、再照 `tls_fingerprint` 回拨它的服务——回拨时
钉子仍然由 TLS 校验，谎报的叶指纹连不上，所以这个承诺不需要额外信任。

`secret` 是**可选字段**：这里"没有它"和上面那一格同一个读法——**键不在，或者值是 null**，都算发送方是
还没有密码概念的旧构建，接收方只用 `code` 完成首次配对；**有值** = 必须逐字相等（常量时间比较：PC
`hmac.compare_digest`，共用内核 `secretMatches` 那个不短路、把每个字符的差异或起来的循环），否则
`403 BAD_PAIR_CODE`（`detail.reason = "passphrase"`）。**空串不是"没有它"，它是一次错误的猜测**——烧掉
那一格来源的一枚名额，答的就是上面那句 `passphrase`；这样"用户在密码框里留了空"永远不会悄悄退成"只认
6 位码"。所以发送方在用户留空时**不要**发送空串，直接省略这个键（PC `if secret:`，内核
`if (secret.length > 0)`），否则旧接收方会把它当成一次错误的猜测。

成功后接收方持久化该 fingerprint 为已配对，并返回随机会话 `token`（32 字节）。后续请求带
`X-Chuanshu-Auth: <token>`。**已配对指纹再次连入时跳过配对码和密码**，但仍会弹一次"是否接收"
确认（见 §4）。

这三个数——`token`、6 位码、8 位密码——是接收方替对端保守的秘密：猜中任何一个就等于顶下那台设备，
所以它们必须由**本平台的密码学随机源**给出（PC `secrets`、安卓 `java.security.SecureRandom`、
鸿蒙 `cryptoFramework.createRandom`、浏览器 `crypto.getRandomValues`），不能是 `Math.random()` 那种
状态可推演的伪随机。字母表与长度照上面那两句；一个字节 256 个值除不尽字母表大小时（10 位数字就是），
要**丢掉**凑不齐的那几个字节再抽下一个，而不是直接取模——取模会让前几个符号比后几个更常出现。
反过来，`peer_id`、offer 与文件的 id、`nonce` 只是标识，合同对它们只要求各不相同（§1、§4），不指定随机源。

别的设备首次配对会拿到 `429 PEER_BUSY`（`detail.reason = "one peer at a time"`，`detail.peer` 是

`session_idle_timeout_s` 没有任何带 token 的请求**都会释放这个名额——最后这条是为了停摆的连接：
对端配上手就再不吭声（应用被杀、手机熄网、发一半人走了），名额不能一直占着让别人进不来。名额被这样
收回去之后，原持有者下一次带旧 token 的请求会拿到 `403 NOT_PAIRED`，它必须重新 pair（已配对的话
不再需要配对码），这是一条正常的重连路径而不是失败。主动连进来的一方同样占这个名额。本机自己拨出去的
那台也算占着：接收方在发起连接成功后把该
fingerprint 登记为当前会话（不新增线上字段，纯本机约定），所以"A 连了 B，C 再连 A"会被拒，
而不是让 A 同时挂两个会话。本机拨出去的那台由发起方自己计时，超时同样登记为已断开。

token 与信任是两件事：token 丢了（接收方重启）请求照样回 `403 NOT_PAIRED`，发送方此时用

一个从未配对的设备即使用同一个 key 签名，也拿不到 token。

安全边界：6 位码有 10⁶ 空间，同一来源攒到 5 次失败就被拒，直到**那五次里最早那一次**满 60 秒——数的是
滑动窗口里还活着的那几条失败，不是"从被锁住那一刻起再等 60 秒"；被锁住期间的尝试只拿 `PEER_BUSY`，
自己不往窗口里添新记录，所以砸得再多也不会把这道锁推远。"来源"是发起方在那条套接字上的地址，按地址分桶；
这份失败清单哪一端都不落盘（重启接收方就清零）。这道锁只数次数与秒数，**不按地址段筛来源**：任何一端都不
检查那个地址是不是局域网内的，因为三端的接收服务**都绑在本机所有接口上**（PC `ReceiveService` 的 `host=""`、
安卓 `srv.bind(InetSocketAddress(port))`、鸿蒙 `address: '0.0.0.0'`）。"只在局域网里可达"在这套东西里只有一个
落点，就是安装器写进系统的那两条规则（`installer/setup.iss` 的 `AllowInbound`：`profile=any` 加
`remoteip=LocalSubnet`，边界由后半句守）——它不在协议里，也不在三端代码里。没跑过安装器的那台机器（从源码跑、
直接双击 `dist` 里那个 exe、Linux 上压根没有规则）第一次监听时是操作系统在弹窗问人，而那一问点下"允许"留下的
规则**远程 IP 是"任何"**、配置文件还写着"公用"。所以这份合同不许任何一端的配对路径按 `192.168.`、`10.` 这类
前缀或 `is_private` 拒绝来源：环回、端口转发、多网卡与跨网段这些真实接法会被自己锁死（§2 的回拨，#111/#149/#154
那几条腿都走 `127.0.0.1` 与 `10.0.2.2`）。要收紧可达范围，改的是那条防火墙规则，不是这份合同。码固定之后
单次锁流不够看，所以强度来自第二层：`k` 是 32 字母表 8 位（约 40 bit 以上），且二维码 + 同屏可见
本来就是这道承诺的实际来源。旧构建只有 `c`，它的安全性和改版前一致——固定码把"每次连接一个新码"
换成了"限流 + 物理可见"，这一点必须让使用两端的人知道。

## 4. 传输

一个 offer = 一次用户可见的传输请求，可含多文件与目录。

```
POST /v1/offer            发送 manifest，等对方作答（最多 offer_wait_timeout_s）
GET  /v1/offer/{id}/state 查询已落盘的分块，用于续传
PUT  /v1/offer/{id}/chunk/{file_id}/{index}   写一个分块，幂等
POST /v1/offer/{id}/finalize                 整文件校验
DELETE /v1/offer/{id}                        中止并清理
```

manifest（这份摊开就是三端今天真发上线的字节，一个不多一个不少）：

```json
{
  "offer_id": "9f1c…",
  "protocol_version": 1,
  "compatible_versions": [1],
  "from": {"peer_id": "3b01…", "name": "PC-A"},
  "total_size": 3145728,
  "files": [
    {"id": "a2b0…", "relpath": "相册/IMG_0001.jpg", "size": 3145728,
     "sha256": "…", "mtime": 1730000000, "type": "image/jpeg"}
  ]
}
```

`total_size` 由发送方求和，接收方不拿它判任何事：v1 没给"总数对不上"留错误码，三端量尺寸一律按
每个条目自己的 `size`（PC 只有命令行应答读这一个数，GUI 与手机连读都不读）。`mtime` 与 `type` 三端
都发、接收方都原样记进台账，但同样不驱动行为：没有哪一端把 `mtime` 写回磁盘时间，也没有哪一处屏
读 `type`——它们今天是在场的字节，不是工作中的字段。

（2026-10-29 第十四轮巡检：这一块的顶层原来只列 `offer_id`/`protocol_version`/`total_size`/`files`，
条目里不列 `type`——而两个发送方（`app/net/send.py:424-431` 与 `cs-protocol.uts::offerJson`）发的

**零字节转义**：鸿蒙的平台 TLS 服务端把请求体交给 JS 时只给到第一个 `0x00` 为止，之后的字节连同
这条连接的读通道一起消失（`.probe/nul.py`：600 B/4 MiB 无零体的请求都完整落到底，把 `0x00` 种在第
300 字节就停在 300）。真实文件里到处是零，所以 PUT 允许换一种线格式：`X-Chunk-Escape: stu`，规则
`0x1B → 0x1B 0x1B`、`0x00 → 0x1B 0x42`，其余字节原样。接收方**只按这个请求头**决定要不要反解，头没有
就是裸体，旧发送方不用改。`X-Sha256` 始终是**原始分块**的摘要，转义只描述字节怎么走过来，不改变内容；
长度校验、幂等、落盘偏移都用反解之后的长度。体里没有零就不转义，所以文本类分块和这条规则之前一样。

**大体的写入节奏**：分块体不是"写完就到位"的。同一条 4 MiB 分块，每 4 KiB 记录之间停 0–10 ms 时，
18 次里有 18 次是"声明的字节一个不少、内容每次都不同"（`X-Sha256` 拦下；`.probe/records.py` 全速 12 次，
`.probe/pace.py` 2/5/10 ms 各 2 次）；停 15 ms 曾经 6 次逐字节相同，2026-10-25 在同一台模拟器上重跑，
15 和 25 都在 1.5 秒内把连接中止掉（手机侧 2303122），只有 40 连续两次 43 秒落对。
50 KB、300 KB、1 MB 全速也能落对。
记录条数不参与这件事——1 KiB 记录 3938 包和 4 KiB 记录 986 包同样全坏，把记录放大到 8 KiB 则是连接当场被
重置。所以坏的是**速率**：管道排不动，不是解析出错。乱的是**顺序**而不是**个数**：那 986 包里第一条永远是
请求行那一包，收了多少字节和用了多少字节相等（`反解` 那一行的两个数字），所以是记录之间换了位置，不是丢包
或多包——没有序号，接收方无法把它们排回去，能做的只有摘要拦下 + 重发。节奏由接收方自己声明：
`GET /v1/hello` 的可选字段
`chunk_pace_ms` = 每 4 KiB 记录之间该停多少毫秒，缺省或 0 就是"随便写多快"；鸿蒙接收方声明 40，PC 不声明。
发送方把声明当成下限，后面再出问题（分块摘要不符，或体写到一半连接死了）就往上升一档重发（0 → 15 → 40），
这一档留给本次会话余下的分块。为什么下限必须来自 hello 而不是"失败一次就学会"：全速的那一次不是只让一个
分块作废，它是把对面整个接收进程打死（`.probe/crashlog.py`），学也无处可学。
档位到头之后连接仍然死掉时，**回复没来不等于体没到**：接收方可以在写完最后一块记录之后、写下响应之前被
中继掐掉（2026-10-25 在 40 ms 上实测到两次，那两次手机自己的 `反解` 行报的是正确摘要）。所以发送方在这里
先读一次 `GET /v1/offer/{id}/state`，对方说齐了就算这一块成了；问到了答案但对方说**没到**，那是管道打嗝而不是
"还是太快"——这一档已经无档可升，2026-10-26 在同一条 fport 隧道上量到 4 MiB 体在 40 ms 上连被吐掉三次、
第四次整块落对——所以发送方用本次剩下的尝试次数把那一块重写一遍。只有问不到答案（对面真没了）、或尝试次数
用尽，才把原来的错误抛出去。
摘要、偏移、幂等都不受节奏
影响，接收方不需要知道发送端有没有停。

`finalize` 的回复（这份摊开也是两端今天真发上线的字节，一个不多一个不少）：

`missing` 就是「只补传该文件的问题分块」里那句"问题分块"的唯一来源：接收方按自己手里那份台账（被整文件
摘要推翻时先作废、答复随之改口成全缺，见下面续传那一节）逐块报缺，发送方只 PUT 这些 index，然后第二次

**这一问可以重投**：验完之后接收方删的是那份续传台账，不是这一单——`finalizeReply` 只给这一单写上
`complete`，PC 也只删 `.chuanshu.state.json`（`receive.py:835-842`），所以表里还有它。2026-10-29 在 PC 上
量到全成之后连投两次，回体都是 394 个字节且逐字节相同（`.probe/r18_before_probe.txt` 第 [3] 行）；
同一趟还量到紧接着问一次 `state` 照样回 200（第 [4] 行）。重投带来一条跟着的义务：**同一份字节只报
一次「这个文件到了」**。一单两个文件、第二个被整文件摘要推翻时，第一趟 finalize 已经替第一个报过一遍，
发送方补完第二个再 finalize，接收方不能再把第一个报第二遍——那是在接收记录和那一声提示里同一个文件
写两行。手机共用内核从 #35 起就有这道闸（`cs-receive.uts:1042-1055` 的 `hasArrival` 在

（`app/ui/transfer.py:2607-2621`），第十八轮补的那三行按落点记的集合只在进程里。2026-10-29 量到这一趟：
一单两个文件、第一个先齐并报过，把接收方停掉再用同一个根目录重开（`adopt_interrupted_offers` 认领下这一单），
补齐第二个再 finalize——第一个文件被报第二遍，同一个落点在列表里两行，而它磁盘上的字节一个都没变（那句

手机的这一半是**结构**给的，不是这一趟量出来的：它的闸问的是持久化的收件台账（`cs-receive.uts:1042-1052` 按

趟探针因此在手机上跑不出 PC 那一行的形状。杀掉接收中的手机再续传，看「收到的文件」会不会多出行，是一趟
设备腿的活（`mobile/README.md` 第 32 条）。

一条 `ok: false` 也可能带回**空的** `missing`，两种来路：这个条目压根没有可补传的块（`size: 0` 的文件三端

finalize 得到同一句拒绝，这一单以 `FILE_DIGEST_MISMATCH` 收尾——同一 offer 里另外那两个文件照常修好。要让
空文件也自愈，得给接收方加一条"finalize 时按 §4 的开档规则把零字节的重新开一遍"的义务，那是三端同改的新
条款，不由巡检签字。

（2026-10-29 第十五轮巡检：这一句原本写的是 `200 {"verified": [{"id": "a2b0…", "ok": true}]}`——线上那条应答
的顶层 `offer_id`、每个条目的 `missing` 与 `path` 都不在纸上，而同一节上面讲落点时已经把 `path` 算进合同了

**续传状态**：接收方每落一块就把手里那份未完成的清单落盘（`state_flush_chunks = 1`，攒到收尾才写会让
中途崩溃白传）。这份文档从不走线，所以放在哪儿是各端自己的事：PC 一单一份，写在 offer 目录下的
`.chuanshu.state.json`（`app/net/receive.py:42`）；两个手机端是一份合并的 `chuanshu-receiver-offers.json`，
未完成的单一条一行（安卓 `CsIdentity.kt:46` 与 `app-android/index.uts:444`，鸿蒙 `app-harmony/index.uts:46`）。
内容体三端相同：`offer_id`、每个条目的 `relpath`/`land`/`size`/`sha256`/已收分块、`created`/`touched`、
`complete`。进程重启后靠它认领未完成的
offer，但**它只是提示**：可信结论只来自 `finalize` 的整文件摘要。状态文件损坏或缺失时，接收方
**什么都不认领**——发送方那份清单再投一次，就是按全缺登记的一单，绝不允许因为状态丢了就谎报已完成。

（2026-10-27 第四轮巡检：这一句原本把 PC 那个文件名当成了合同位置——「重写 offer 目录下的

以前这一句写的是「按"已落盘字节 / chunk_size"重算缺块」，而这个字节数三端都量不出来：用户在卡片上点
「接受」的那一刻，接收方就按清单里声明的长度把文件开好（PC `app/net/receive.py:938`
`handle.truncate(size)`、鸿蒙 `app-harmony/index.uts:1049` `fs.truncateSync(fd, size)`、安卓
`app-android/CsStore.kt:52` `raf.setLength(want)`），一块没写的文件长度也等于全长——先开档是
`STORAGE_FULL` 能在把 4 GiB 写花之前回给用户的那一手（#128 的预分配）。所以宁可放弃「按字节猜缺哪几块」
这条捷径，也不撤销提前开档：丢的只是那几块本来要重传的字节，分块的偏移、幂等与整文件摘要都不受影响，
重投的那一单照样把每一块写回同一个位置。
一份被整文件摘要推翻的台账，它记下的缺块列表也一并作废：接收方要当场抹掉这个文件的分块记录，
`finalize` 的回复随之改口成全缺。留着它，发送方最后那一手（整单重发）会被逐块的幂等答复挡回来——
每个分块都被回答"已经存过"，一个字节也写不回去，这一单就再也回不来（2026-10-26 在安卓与鸿蒙模拟器上各量到一次，
`.probe/a_127.txt`、`.probe/h_127.txt` 的第二条腿）。
`finalize` 里每个文件都 `ok: true` 之后，这份状态就没有可续的东西了，接收方应当删掉它——
留在盘上会让下次重启把一次已经完成的传输重新当成未完成的 offer 认领回来。

**闲置 offer 回收**：一个被接受、却始终没写完成的 offer 也是一份占用：它预先开好的稀疏文件和
那份状态会一直挂在接收方的表里。距最后一次落块超过 `offer_idle_timeout_s` 就可以按"对方不来了"
丢掉它（等同一次 `DELETE /v1/offer/{id}`：删半截文件与状态，`offer_id` 从表里消失）。这条窗口取
得比任何合法的等待都宽——接收方自己为腾空间而 park 一个 offer 的上限也在同一量级，回收不许抢在
park 到点之前。被回收之后，迟到的分块拿到 `404 OFFER_UNKNOWN`，发送方要么整单重发（新的
`offer_id`），要么放弃；这不是错误码的失败，而是这单传输已经结束。

**HTTP 层保活陷阱**：接收方在*读完请求体之前*回错误，残留的 body 会被对端当成下一个请求行
解析，连接从此错乱。所以错误响应必须先吞掉未读的 body（≤64 KiB，PC 那个数是 `receive.py:48` 的
`_MAX_DRAIN`），吞不动就**不再复用这一条连接**。这一句从前写的是「吞不动就置 `Connection: close`」，
而那个头恰恰不是三端共用的写法：PC 在这一支只置 `close_connection`（`app/net/receive.py:250-255`），
头里不写那三个字，但这条套接字当场不再接第二个请求；安卓每一句应答都带着那个头
（`app-android/CsServe.kt:181`）；鸿蒙既不写它也不复用（`app-harmony/index.uts:2292-2312` 写完自己关，
`closeLater` 隔 300 毫秒再拆——2287-2291 那段记的就是为什么不敢写）。在这台鸿蒙设备上那个头是有
坏处的：#121 量到对端要了 `Connection: close` 之后，承载请求体的那一条 TLS 记录丢在拆除里，接收方
只看见一个声明了长度、没有一个字节的头。所以这条合同管的是**别让第二个请求行踩进同一根连接**，
不是必须写哪一个头。

发送方看到连接被关要重连重发一次，这属于实现细节而不是错误码。两端本来就每条请求重拨一条新
连接（PC 那段注释在 `send.py:256-261`），所以"重发"对这一端等于再拨一次、原样再问一遍；管到的
请求不一样宽。PC 在传输层——每一条请求都有第二趟（`for attempt in (0, 1)`，`app/net/send.py:255`；
2026-10-29 把第一趟拧成 `ConnectionResetError`，第二趟照样拿回那份 200，`.probe/r18_before_probe.txt`
第 [1] 行）。手机在路由层——读不到应答的那一支各归各的规矩管：清单那一问一秒后再问（上面
「待决应答」），分块那一问先问一次 `state`（上面「节奏」）。**`finalize` 这一问改前没有第二趟**：
`status == 0` 落进 `status != 200` 那一支，整单被报成失败，而对面很可能已经验完收下（这一端只是
没读到那句回答）。本轮按上面那句「这一问可以重投」给它补了一趟——一秒后重问一次，只一次
（`cs-client.uts:488-491`）。

## 5. 路径清洗（接收方的安全底线）

`relpath` 是发送方给的字符串，接收方**必须**假定它是敌对的：

- 分隔符统一为 `/`；拒绝 `\`、`:`、盘符、前导 `/`
- 拒绝任何 `..` 段，以及**一切**以 `.` 开头的段。这一条不分辨"哪几个点开头的目录算保留"：接收方看见
  段首是点就拒（`.git`、`.chuanshu` 是它要防的形状，不是它划的范围）。发送方（PC 与手机）也按段拦，
  所以这个名字两头都走不通
- 「发送方也按段拦」这一句改前只在叶子名上成立。PC 的 `plan()` 从 `rglob("*")` 拿到的是整棵树，而过滤那行读的是
  `entry.name.startswith(".")`——`工程/.git/config` 的叶子是 `config`，它照样进了清单，relpath 带着 `.git` 那一段上线。
  量到的（`.probe/r20_before_probe.txt`）：带 base 那一趟（GUI 拖目录、CLI `--base` 走的都是这一趟）整份清单换来一个
  `400 PATH_REJECTED`、`detail.segment` 写 `.git`，这一单一个字节都没谈成，同目录里那两份无辜的（`读我.txt`、
  `相册/照片.bin`）一个都没落地；把 base 摘掉反倒传得出去，而那份 `.git/config` 被拍平成 `config` 落在对面——
  按段判的是接收方，叶子名的过滤管不住它换成另一条路径。改后 `plan()` 把 relpath 与「这一份摊开在自己所选根目录下的
  路径」各按段判一次（`app/net/send.py:168` 的 `_has_dot_segment`），两种形状都报不出点段，那份 `config` 也不再出现
  （`.probe/r20_after_probe.txt`）。清单被拦空了以后两头都有话：GUI 说「这里没有可发的文件。」、CLI 说
  「要发的东西里没有文件。」，不会把一份空单发上线。手机的这一半不是这段过滤给的：它没有目录遍历
  （`uni.chooseFile` 交出来的是平铺的叶子名），而 `cs-client.uts:127-141` 的 `pathCheck` 问的就是整条 relpath，
  逐段判，违规整单不发
- 保留名 `CON PRN AUX NUL COM1-9 LPT1-9`（取点号前那一段，不分大小写）与尾随的 `.`/空格：**每个接收方都拒，
  不看自己跑在什么系统上**。这条要求本是 Windows 的，但一个名字能不能落地不该取决于这一单今天落在哪台机器上——
  同一份清单今天发给 Linux，明天可能就发给一台 Windows
- 单段名字超过 `max_name_bytes` → `400 PATH_REJECTED`
- 一条 `relpath` 切出的段数（连文件名本身一起数）超过 `max_path_depth` → `400 PATH_REJECTED`；正好等于它是
  收的。这道闸门是给接收方自己的目录树封顶，不是给发送方的额度
- 一份清单的文件数超过 `max_files_per_offer` → `400 UNSUPPORTED_PROTOCOL`，`detail.reason` 写 `too many files`。
  v1 的错误码表里没有"太大"这一格，换码属 §7 的兼容决定；发送方（PC 与手机）都在本地按同一个数拦下，
  不会把这问发到线上
- 落盘位置固定为 `<接收目录>/<offer_id>/<清洗后 relpath>`，每个 offer 一个隔离目录，
  绝不直接写入用户选定的根目录；同名文件加 ` (2)` 后缀而非覆盖
- 符号链接、重解析点：写出前 `resolve()` 一次，若结果不在该 offer 目录内 → 拒绝

这条清单两端都得实现，PC 与手机互为接收方。

## 6. 保活与后台（各端各自的坑，不在协议里却决定成败）

- PC：常驻托盘即可，监听随进程存活。
- Android：接收中需前台服务（`dataTransfer` 类型，Android 14 正式版里这一类型改名为 `dataSync`；
  对应权限 `FOREGROUND_SERVICE_DATA_SYNC`）+ 13+ 通知权限，否则系统会掐连接。
- iOS：**App 退后台后监听 socket 不再接受新连接**。协议层无法绕过，UI 必须在"接收中"
  状态显示"请保持传书在前台"，而不是让用户以为在收。
- 鸿蒙 Next：同 iOS 的后台限制口径，按真机实测结论写进 UI 文案。

这是把"手机当接收方"的成本从协议层挤到 UI 层的地方——不做隐藏，直接显示。

## 7. 版本与兼容

`compatible_versions` 列出双方都能跑的版本集合，取交集非空才继续；否则
`400 UNSUPPORTED_PROTOCOL`。字段只增不改语义；要改语义就升 `protocol_version`。

这个集合出现在每一处"说自己"的场合：`hello`、`pair` 的应答，以及 `pair`/`offer` 的请求体。
写在请求体里不是因为 hello 可以省——是因为接收方不会回拨去读对方的 hello，对方的集合只可能
从这两个请求体里拿到。请求体不带这个字段，就按它印出的 `protocol_version` 那一个数当作整个
集合：那是这个字段之前的一版，不是把它当陌生人的理由。

`hello` 里还有一个 `features`，别把它读成第二套兼容规则：三端都照 `transport.hello_features`
那一份名单原样发（v1 是 `resume`、`chunk-hash`、`directory`）。**v1 没有任何一端拿它做决定**——
能不能谈只看上面那个交集。这条句子写下来是给下一位读它的人的：不许因为名单里多一个词或少一个词
就改判这一单的去留；要让它决定什么，先按上面那句「改语义就升 `protocol_version`」办。

## 8. 云中转分支

`cloud-relay` 分支不复制本契约，只替换寻址：peer 把七个端点当成对中继的调用，
`peer_id` 换成中继侧 session id，鉴权多一层账号。发现/配对语义保持一致，
因此 LAN 版和云版可以共用同一份 fixture 做回归。

## 9. 冻结标准

v1 视为冻结的条件：`py scripts/protocol_selftest.py`（Windows 的启动器；Linux 上是
`python3 scripts/protocol_selftest.py`，同一份脚本、同一条链）用**同一份代码**跑通
配对 → 多文件含目录 → 中途断开 → 续传 → finalize 全绿，且错误码表两端各能渲染出
中英文文案。参考实现即验收工具，不接受只写在文档里的约定。链条里「多文件含目录」那一格判的是
落点，不是清单：至少一条 `relpath` 带目录段，而它落下来的路径把目录段留着，没有摊平成文件名。

PC 端已于 2026-10-19 达成（51 条断言，含"杀掉接收进程再拉起"的真重启路径，以及 mDNS + UDP
两条通道各自真的发现了对端；逐条读数打在 `.probe/protocol_report.txt`，那是跑出来的本地产物、
不入库）。手机端接入时必须用**同一份 `protocol.json` 和同一组 fixture**重跑一遍，只认它自己那端的
绿色结果。这两样东西各自是什么，写在这里免得被读成一件还没发出来的工件：同一份 `protocol.json`
是 `mobile/shared/protocol/` 下那份逐字节副本，上游改了就重跑 `mobile/scripts/vendor_protocol.py`，
镜像守卫按 `SOURCE.json` 的戳核它；同一组 fixture 没有单独存过文件，共享的是上面那一条序列和同一张
错误码表，各端把它复述成自己的腿。手机端那一趟就是 `接收内核自检`（浏览器档，两个宿主的编译门各自
`rc=0`），不是 PC 那一份读数的复制。
